## 1. Пирамида данных (DIKW). Ускорение обработки информации с помощью технологий business Intelligence 

**DIKW** (англ. data, information, knowledge, wisdom — «данные, информация, знания, мудрость»)
Данные - неструктурированы
Информация - данные обработаны и структурированы, есть контекст. Можно сказать кто, что, когда, сколько и т.д.
Знание - Фильтрация и переработка информации, которая позволяет делать выводы. Если А, то Б.
Мудрость - Применение знаний для определённых решений. Следует сделать Решение Р, чтобы повысить Б.

Business Intelligence (BI) — это технологии и инструменты для анализа данных и поддержки принятия решений. Ускорение достигается за счет:

1. **Автоматизации сбора и интеграции:** ETL-процессы (Extract, Transform, Load) автоматически загружают данные из разных источников (БД, CRM, ERP) в единое хранилище (Data Warehouse), экономя время на рутинной работе.
2. **Специализированных структур данных:** Использование **OLAP-кубов** (см билет 34) и **индексов** в хранилищах данных позволяет выполнять сложные аналитические запросы к миллионам записей за секунды.
3. **Предварительной агрегации и вычислений:** Ключевые показатели (KPI), отчеты и дашборды заранее рассчитываются и обновляются по расписанию, предоставляя информацию мгновенно.
4. **Интуитивной визуализации:** Инструменты (Power BI, Tableau) превращают сложные данные в графики и диаграммы, что ускоряет их восприятие и выявление трендов человеком.
5. **Самообслуживания (Self-Service BI):** Пользователи (не IT-специалисты) могут сами строить отчеты, не дожидаясь запроса к отделу разработки, радикально сокращая цикл "вопрос-ответ".

## 2. Трехуровневая система организации базы данных от ANSI. Логическая и физическая независимость данных 

По трёхуровневой системе организации в БД выделяется три уровня:
1. Внешний - Уровень представлений. То, с чем работают пользователи. Разным пользователям разные внешние уровни.
2. Концептуальный - Логическая структура всей БД. Описывает хранимое в БД, таблицы, связи, схеми.
3. Внутренний - Физическое хранение данных. Структуры файлов, типы записей, методы сжатия, расположение на диске и т.д.

Связь между уровнями идёт за счёт системы отображения (mapping).

#### Логическая и физическая независимость данных

Логическая независимость - независимость внешних схем от концептуальных. Меняем таблицы (добавляем таблицы, связи, столбцы) - внешний уровень не меняется, остаётся таким же.

Физическая независимость - независимость концептуального и внешнего уровней от внутреннего. Можно поменять СУБД, поменять диски, добавить индекс, но другие уровни не изменятся.

## 3. Основные требования к системе управления базами данных. 

Требования к СУБД:
- Доступность данных - можно достучаться
- Согласованность данных - БД не должна быть противоречива
- Целостность данных - защита от некорректных изменений
- Метаописание данных - системный каталог с описанием данных
- Восстановление данных - откат к целостному состоянию после сбоев
- Обмен данными - импорт/экспорт
- Обработка данных в рамках транзакции - поддержка атомарности
- Контроль за доступом к данным - управление доступом

## 4. Хранение данных: SDD, HDD, Flash Memory, NAS Disk и др. 

- Flash память самая дорогая, энергозависимая, но быстрая
- NAS Disk - сетевое хранилище данных
- Облачное хранилище - Виртуализированная инфраструктура (часто на базе SSD/HDD)

## 5. Терминология реляционных баз данных: отношение, сущность, атрибуты, домен, ключ. Приведите поясняющие схемы. 

Отношение:
Структура данных, представляющая собой **таблицу** (набор строк и столбцов), которая хранит информацию об одном типе объектов. Условно таблица "Студенты"

Сущность:
Реальный или абстрактный объект предметной области.
```
[Студент]   (сущность на ER-диаграмме)
    |
    V
Таблица STUDENTS (отношение в БД)
```

Атрибут:
Характеристика или свойство сущности. В таблице атрибуту соответствует **столбец (поле)**.
 ```
Сущность: [Студент]
Атрибуты: | student_id | name | birth_date | group_id |
          (столбцы таблицы STUDENTS)
 ```

Домен:
Множество **допустимых значений** для одного или нескольких атрибутов. Это понятие типа данных + ограничений.

Ключ:
Минимальный набор атрибутов, который характеризует определённую сущность в отношении. Есть несколько типов.

- Первичный ключ - уникальный идентификатор(ы) строки
- Внешний ключ - атрибут-ссылка на объект другого отношения (таблицы)
(не говорилось на лекциях) 
- Потенциальный ключ - атрибут, который мог бы стать первичным ключом (уникален и неизбыточен).
- Суперключ - набор атрибутов, избыточно идентифицирующий строку.

## 6. Правила реляционной модели: с нулевого по пятое правило. 

Список правил:
0. Основное правило - Система способна управлять базами данных, используя исключительно свои реляционные возможности
1. Информационное правило - вся информация в реляционной БД (РБД) на логическом уровне должна быть явно представлена только значениями в таблицах
2. Правило гарантированного доступа - в реляционной БД каждое отдельное (атомарное) значение должно быть логически доступно с помощью комбинации имени таблицы, значения первичного ключа и имени столбца.
3. Систематическая поддержка отсутствующих значений - значения типа NULL (неопределённые, неизвестные) должны поддерживаться для всех типов данных, например, для числовых данных отсутствующие значения не эквивалентны нулевым.
4. Доступ к словарю данных в терминалах реляционной модели - словарь данных должен сохраняться в форме реляционных таблиц и СУБД должна поддерживать доступ к нему при помощи стандартных языковых средств.
5. Полнота подмножества языка - система управления РБД должна поддерживать хотя бы один реляционный язык, который:
	1. Имеет линейный синтаксис
	2. Может использоваться как интерактивно, так и в прикладных программах
	Технически это язык SQL.

---

## 7. Правила реляционной модели: с шестого по двенадцатое правило. 

6. Возможность изменения представлений - каждое представление должно поддерживать все операции манипулирования данными, которые поддерживают все операции манипулирования данными, которые поддерживают реляционные таблицы: выборка, изменение, удаление
7. Наличие высокоуровневых операций управления данными - вставка, удаление, редактирование
8. Физическая независимость данных - приложения не должны зависеть от используемых способов хранения данных на носителях, от аппаратного обеспечения компьютеров, на которых находится РБД
9. Логическая независимость данных - представление данных в приложении не должно зависеть от структуры реляционных таблиц. Если в процессе нормализации одна реляционная таблица разделяется на две, представление должно обеспечить доступ к данным
10. Независимость контроля целостности - вся информация, необходимая для поддержания целостности, должна находиться в словаре данных. Язык для работы с данными должен выполнять проверку входных данных и автоматически поддерживать целостность данных
11. Независимость от расположения - база данных может быть распределённой, может находиться на нескольких ПК и это не должно оказывать влияния на клиентскую часть приложения.
12. Согласование языковых уровней - если используется низкоуровневый язык доступа к данным, он не должен игнорировать правила безопасности и правила целостности

## 11. Операция декартово произведения. Примеры в виде диаграмм Венна, записи в виде формул и табличном формате. 

В виде диаграммы Венна не отображается. Фото:
![[Pasted image 20260107134233.png]]
По сути перемножение всех элементов A на все элементы B.

```
A = {a₁, a₂}      B = {b₁, b₂, b₃}

A × B = {
  (a₁, b₁), (a₁, b₂), (a₁, b₃),
  (a₂, b₁), (a₂, b₂), (a₂, b₃)
}
```

- **Теоретико-множественная нотация:**  
`R = A × B`

- **Реляционная алгебра:**  
`R ← A × B`

SQL:
```SQL
SELECT * FROM A
CROSS JOIN B;
-- или просто через запятую (неявное соединение):
SELECT * FROM A, B;
```

Таблицей:
A:
```SQL
color_id | color_name
---------|-----------
1        | Красный
2        | Синий
```
B:
```SQL
size_id | size_name
--------|----------
S       | Маленький
L       | Большой
```

`R= A × B
```SQL
color_id | color_name | size_id | size_name
---------|------------|---------|----------
1        | Красный    | S       | Маленький
1        | Красный    | L       | Большой
2        | Синий      | S       | Маленький
2        | Синий      | L       | Большой
```

Порядок важен, `A × B != B × A`. Ибо изменится порядок. Хотя и в SQL получатся те же множества, просто с разным размещением столбцов.

## 12. Операция проекции. Примеры в виде диаграмм Венна, записи в виде формул и табличном формате. 

Проекция отношения (таблицы) — это операция, которая **выбирает указанные столбцы (атрибуты)** и **удаляет дублирующиеся строки** из результата.

```
Исходная таблица (3D пространство):   Проекция на плоскость (x,z):
(x₁, y₁, z₁)                           (x₁, z₁)
(x₂, y₂, z₂)      → π_{x,z} →         (x₂, z₂)
(x₃, y₃, z₃)                           (x₃, z₃)
```

- **Реляционная алгебра:**  
`R ← π_{атрибут1, атрибут2, ...}(Исходное_отношение)`

SQL:
```SQL
SELECT DISTINCT column1, column2, ...
FROM table_name;
```

Два варианта записи:
- $\pi_{B}(R)$
- R\[B\]
Где R - изначальное множество, B - выбранные измерения (столбцы, атрибуты)

## 13. Операция естественного соединения. Примеры в виде диаграмм Венна, записи в виде формул и табличном формате. 

Естественное соединение двух отношений A и B — это отношение, содержащее **все возможные комбинации строк из A и B, у которых совпадают значения одноименных атрибутов**, причем в результате **повторяющиеся столбцы устраняются**.

Это вроде декартового произведения, но с ограничением по совпадению опрелённых полей.

- **Реляционная алгебра:**  
`R ← A ⋈ B` (специальный символ "bowtie")

SQL:
```SQL
SELECT * FROM A
NATURAL JOIN B;
```

В виде таблиц.
A:
```SQL
emp_id | emp_name  | dept_id
-------|-----------|--------
101    | Иванов    | D01
102    | Петрова   | D01
103    | Сидоров   | D02
104    | Кузнецов  | D03
```

B:
```SQL
dept_id | dept_name  | location
--------|------------|----------
D01     | IT         | Москва
D02     | HR         | СПб
D04     | Sales      | Казань
```

R:
```SQL
dept_id | dept_name  | location
--------|------------|----------
D01     | IT         | Москва
D02     | HR         | СПб
D04     | Sales      | Казань
```

Выбирается общее поле (поля), по нему идёт внутреннее соединение.

По сути `A INNER JOIN B ON A.dept_id = B.dept_id`
`A ⋈ B = B ⋈ A`
`(A ⋈ B) ⋈ C = A ⋈ (B ⋈ C)`
`A ⋈ B ⊆ A × B` (меньше или равно декартовому соединению)

## 14. Типы соединений: SQL JOIN. Диаграммы Венна и примеры запросов на языке SQL. 

### INNER JOIN

Внутреннее соединение. Берёт только такие пары, где и слева, и справа есть какое-то значение.

### LEFT JOIN (RIGHT JOIN)

Внешнее соединение. Берёт все строки из одной таблицы (левой или правой) и пытается соединить со всеми строками второй таблицы по условию. Если не получается - делает запись, где половинка - NULL.

### FULL JOIN

Полное внешнее соединение. Берёт все строки из левой и все строки из правой. Если что-то не сходится по парам, то вставляет такие записи с NULL во второй части.

### CROSS JOIN
Декартово произведение. Создаёт пары из каждой левой строчки с каждой правой.

На таблицах:
A:
```SQL
customer_id | name
------------|---------
1           | Иванов
2           | Петрова -- Клиент без заказа
3           | Сидоров
```
B:
```SQL

---------|------------|--------
100      | 1          | 5000
101      | 1          | 3000
102      | 3          | 7000
103      | NULL       | 1000  -- Заказ без привязки к клиенту
```

Inner:
```SQL
name    | order_id | amount
--------|----------|--------
Иванов  | 100      | 5000
Иванов  | 101      | 3000
Сидоров | 102      | 7000
```

Left:
```SQL
name    | order_id | amount
```

## 15. Операция деления отношений. Примеры записи в виде формул и табличном формате. 

- **Реляционная алгебра:**  
`R ← A ÷ B`

- **Смысл:** `R = { x | ∀ y ∈ B, (x, y) ∈ A }`  
где x — кортеж из атрибутов A-B, y — кортеж из атрибутов B.

**"Множество всех таких кортежей x, что для КАЖДОГО кортежа y, принадлежащего отношению B, объединенный кортеж (x, y) принадлежит отношению A."**

- **SQL:** Нет прямой операции, эмулируется через EXISTS/NOT EXISTS или GROUP BY.
Визуально на таблицах попроще:

```SQL
Студенты и курсы:
student_id | course_id
-----------|----------
S1         | C1
S1         | C2
S1         | C3
S2         | C1
S2         | C2
S3         | C1
S4         | C1
S4         | C2
S4         | C3
```

```SQL
Нужные курсы:
course_id
----------
C1
C2
C3
```

Операция деления даст:
```SQL
student_id
----------
S1        ← Прошел C1, C2, C3
S4        ← Прошел C1, C2, C3
```

Почему?
Смотрит все уникальные Student_id, у которых есть связь со всеми course_id из таблицы B. У S2 и S3 нет связей с какими-то из course_id (С3 для S2; С2, С3 для S3)

Может быть составным.

**Отношение `Поставки` (A):**
```SQL
supplier_id | part_id | project_id
------------|---------|-----------
S1          | P1      | J1
S1          | P2      | J1
S1          | P3      | J1
S1          | P1      | J2
S2          | P1      | J1
S2          | P2      | J1
S2          | P1      | J2
S2          | P2      | J2
S3          | P2      | J1
```

**Отношение `Требуемые_Детали_Для_Проекта` (B):**
```SQL
part_id | project_id
--------|-----------
P1      | J1
P2      | J1
```

**Операция: `Поставки ÷ Требуемые_Детали_Для_Проекта`**  
_Вопрос: "Какие поставщики поставили ВСЕ требуемые детали для проекта J1?"_

```SQL
supplier_id
------------
S1          ← Поставил P1 и P2 для J1
S2          ← Поставил P1 и P2 для J1
```

Как это в SQL:
```SQL
SELECT student_id
FROM Студент_Курс
WHERE course_id IN (SELECT course_id FROM Требуемые_Курсы)
GROUP BY student_id
HAVING COUNT(DISTINCT course_id) = (SELECT COUNT(*) FROM Требуемые_Курсы);
```

#### **1. Прикладные программы**

- Внешние программы, которые используют СУБД для хранения данных.
    
- **Примеры:** CRM-система, банковское ПО, веб-сайт (через ORM).
    

#### **2. Интерфейс доступа**

- Библиотеки и драйверы для подключения приложений к СУБД.
    
- **ODBC/JDBC** — стандартные кроссплатформенные интерфейсы.
    
- **ORM** (Hibernate, Entity Framework) — объектно-реляционное отображение.
    
- **Собственные API** — оптимизированные драйверы от вендоров.
    

#### **3. Процессор запросов (Query Processor)**

- **Сердце СУБД**, преобразует SQL-запросы в исполняемый код.
    
- **Парсер** — проверяет синтаксис, строит абстрактное синтаксическое дерево.
    
- **Транслятор** — конвертирует в внутренний формат (например, реляальную алгебру).
    
- **Оптимизатор** — самый сложный компонент: анализирует возможные планы выполнения, использует статистику по данным, выбирает оптимальный план (например, какой индекс использовать, порядок соединений).
    
- **Исполнитель** — выполняет выбранный план, обращаясь к менеджеру памяти за данными.
    

#### **4. Менеджер памяти (Buffer Manager)**

- **Кэш между диском и процессором запросов**.
    
- Управляет буферным пулом — областью ОЗУ, куда загружаются страницы данных с диска.
    
- Реализует алгоритмы замещения страниц (LRU — Least Recently Used).
    
- Снижает количество физических обращений к диску (самое медленное место).
    

#### **5. Менеджер транзакций (Transaction Manager)**

- **Гарантирует ACID-свойства**.
    
- **Менеджер блокировок** — обеспечивает изоляцию транзакций (реализует уровни изоляции через блокировки или MVCC).
    
- **Менеджер журнала** — ведет журнал транзакций (WAL — Write-Ahead Logging): сначала запись в журнал, потом в данные.
    
- **Менеджер восстановления** — обеспечивает откат транзакций при ошибках и восстановление после сбоев с помощью журнала.
    

#### **6. Менеджер данных (Data Manager)**

- **Управляет физическим хранением данных**.
    
- **Файловый менеджер** — работа с файлами БД, управление страницами (обычно 4-16 КБ), выделение места.
    
- **Менеджер индексов** — создание, поддержка и использование индексов (B-деревья, hash-индексы).
    
- **Менеджер метаданных** — хранит системный каталог (информацию о таблицах, столбцах, индексах, правах доступа).
    

#### **7. Дисковая подсистема**

- **Физическое хранилище** — файлы на диске (SSD/HDD).
    
- **Файлы данных** — основные файлы с таблицами и индексами.
    
- **Файлы журнала** — журнал транзакций для восстановления.
    
- **Конфигурационные файлы** — настройки СУБД.

## 17. Модели реализации баз данных: реляционные, сетевые, иерархические. Примеры 

### 1. Иерархическая модель (1960-е, основная в IMS IBM)

Древовидная структура. Родитель-потомок.
```
          КОРПОРАЦИЯ
            /    \
       ДЕПАРТАМЕНТ ПРОЕКТ
         /    \        \
СОТРУДНИК ОТДЕЛ    ЗАДАЧА
```

- **Строгая иерархия:** У записи только один родитель (кроме корня).
- **Связи:** 1:N (один ко многим).
- **Навигационный доступ:** Программист должен знать путь (например, от департамента к сотруднику).
- **Пример:** `КОРПОРАЦИЯ → ДЕПАРТАМЕНТ "Финансы" → СОТРУДНИК "Иванов"`.

**Пример СУБД:** IBM IMS, Windows Registry.

### 2. Сетевая модель (CODASYL, 1971)

**Структура:** Граф, где запись может иметь несколько родителей.
```
         СТУДЕНТ
        /       \
   ЗАЧЕТКА ← КУРС
        \       /
         ПРЕПОДАВАТЕЛЬ
```

- **Связи:** M:N (многие ко многим) через "типы связей".
- **Сложная навигация:** Программист идет по указателям (сетям) от одной записи к другой.
- **Пример:** `СТУДЕНТ "Петров" → (связь "посещает") → КУРС "Базы данных" → (связь "ведет") → ПРЕПОДАВАТЕЛЬ "Сидоров"`.

**Пример СУБД:** IDMS, Integrated Data Store.

### 3. Реляционная модель (Эдгар Кодд, 1970)

**Структура:** Таблицы (отношения) со строками и столбцами.

```
СТУДЕНТЫ (student_id, name)          ОЦЕНКИ (student_id, course_id, grade)
     1       Иванов                       1          101         A
     2       Петрова                      1          102         B

КУРСЫ (course_id, title, teacher_id)   ПРЕПОДАВАТЕЛИ (teacher_id, name)
     101     Базы данных      201               201       Сидоров
```

- **Декларативный доступ:** `SELECT * FROM СТУДЕНТЫ WHERE name='Иванов'` (СУБД сама находит путь).
- **Связи через ключи:** Внешние ключи связывают таблицы логически.
- **Теоретическая основа:** Реляционная алгебра/исчисление.
- **Независимость данных:** Физическое хранение отделено от логической схемы.

**Пример СУБД:** Oracle, MySQL, PostgreSQL, SQL Server.

## 18. Классификация СУБД по архитектуре: встроенные, файл-сервер, клиент-серверные. Схемы. 

### 1. Встроенные (Embedded) СУБД

**Архитектура:** Библиотека, линкуемая непосредственно с приложением.
- **Нет сетевого взаимодействия** — все в одном процессе.
- **Нет отдельного серверного процесса** — СУБД как библиотека.
- **Файл-ориентированные** — данные в обычных файлах ОС.

### 2. Файл-серверные СУБД

**Архитектура:** Данные в общем файле на сервере, логика обработки на клиенте.
- **"Толстый клиент"** — СУБД-движок на каждой клиентской машине.
- **Сервер только для файлов** — передает целые файлы/страницы по сети.
- **Примеры:** Microsoft Access (через общий файл .mdb), Paradox, FoxPro.

### 3. Клиент-серверные СУБД

**Архитектура:** Разделение логики: сервер обрабатывает данные, клиент — интерфейс.
- **"Тонкий клиент"** — только интерфейс и отправка запросов.
- **Централизованная обработка** на сервере — выполнение SQL, транзакции, безопасность.
- **По сети передаются только запросы и результаты** (не файлы данных).
- **Примеры:** Oracle, Microsoft SQL Server, PostgreSQL, MySQL (в клиент-серверном режиме).
